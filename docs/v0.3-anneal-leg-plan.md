# v0.3 WSD anneal-leg plan (2026-07-20)

Approved execution plan for the anneal leg of run xzcb60bl. Committed on
PR #10 per release-transparency practice; the same content is posted as a
PR comment and summarized in the W&B run notes.

## Context

The long-horizon run (xzcb60bl) early-stopped at 65,250 on the WSD *plateau*
— its scheduled 11k-step LR→0 anneal never ran. Round-3 probe **R5** showed
WSD+anneal beats the plateau on ALL metrics, and the hardening pass built
`configs/tpu/stage2_tpu_v6e16_full_v03_mh_anneal.yaml` + live-drilled the
exact resume mechanics (Phase-E spoke 4: resume plateau ckpt, extend
max_steps, WSD total = start+anneal ⇒ resume lands directly in the anneal).
The idle v6e-16 slice is still up. Expected cost: **11,000 steps ≈ 7.5–8 h**
at the measured all-in rate; expected outcome: a new best val composite
below 2.9048 (R5 evidence; no promised magnitude).

## Hyperparameters (all pre-registered/validated — zero new knobs)

| knob | value | why this is the best choice |
|---|---|---|
| resume anchor | **step 65,250** (latest, same save_dir, `--resume auto`) | Template's design, Phase-E-drilled. Contiguous experiment: same W&B run (resume re-attaches xzcb60bl), monotonic global_step, no duplicate steps in the public suite. Annealing from best-62,750 would fork 2,500 steps of duplicate global-steps with different weights (messy suite/W&B) for a 0.0036 val difference on a flat plateau — not worth it. Optimizer+RNG restore from GCS is the 4×-drilled path. |
| `max_steps` | **76,250** (= 65,250 + 11,000) | The template's single FILL field. |
| `wsd_anneal_steps` | **11,000, linear → 0** | The LOCKED recipe's pre-registered anneal length (MiniCPM-style ~10%); = 14.4% of the effective 76,250 horizon — inside the 10–20% sweet spot from the WSD literature; linear shape is what R5 validated. Not re-tuned: inventing a new length would un-lock the recipe without sweep evidence. |
| LR path | plateau **1.716e-4 → 0** over [65,250 → 76,250] | WSD schedule with the new total; warmup (1,100) is long past; all 7 param-group LRs scale down together as in R5. |
| `early_stop_patience` | **0** | Fixed-length descent by design — never early-stop inside the anneal. |
| everything else | **byte-identical** to the long-run config | Global batch 32, clip 1.0, loss weights + (completed) curriculum, seed 42, val gate 3,200 × every 250, save every 1,000 keep-all, audio demos at 70k/75k. Data order continues deterministically from step 65,250 (mid-epoch 2). |

## Execution steps

1. **Config**: fill the template —
   `max_steps: 76250`; update its two stale pre-restart identity fields to
   the -r2 run (`save_dir: …/stage2-v6e16-mh-v03-r2`,
   `wandb_run_name: v0.3-long-horizon-mh-r2`; header note). Commit.
2. **Code to deploy = current HEAD** (deltas vs the run's 6dcc9e1 are
   logging/provenance-only: topology derivation, warnings filter, hub-log
   dedup, `save_embedding_layers`, storage-limit circuit breaker, env
   hygiene — no training math; 184 tests green). Pin tarball
   `gs://tinyaya-stage2-eu/code/mh-<sha>.tar.gz`.
3. **Preemption self-heal FIRST** (sequencing lesson from the restart):
   node metadata → anneal config-file + new tarball pin; `launch.env` →
   same; verify the local `qrwatch` tmux survived the user's power outage
   (restart it if dead).
3b. **W&B run notes (user requirement)**: since the anneal CONTINUES run
   `xzcb60bl`, append a detailed "Anneal leg (2026-07-20)" section to that
   run's notes BEFORE launch: the full hyperparameter table from this plan
   (resume anchor 65,250, max_steps 76,250, wsd_anneal_steps 11,000 linear
   → 0 from 1.716e-4, early_stop off, everything-else-identical), the
   deployed code sha, the R5 evidence pointer, expected ~8 h duration, and
   the launch-verification gates — so anyone opening the run can follow
   exactly what was done and why. Post-run: append the outcome (new best,
   final val) to the same notes.
3c. **PR #10 (user requirement)**: commit the filled anneal config + this
   plan document to the branch (plan text also saved as
   `docs/v0.3-anneal-leg-plan.md` so it's versioned, not just chat), and
   post the full plan as a PR #10 comment before launch.
3d. **do.md (user requirement)**: new Open entry "Add anneal-leg details +
   results to the model card (post-anneal)" — card gets the anneal section
   (schedule chart note, new best, updated checkpoints table/ladder) after
   the run completes.
4. **Launch** via `hot_redeploy.sh` on the idle slice
   (`CONFIG_FILE=…_mh_anneal.yaml`, `TPU_STRATEGY=fsdpv2_lora`,
   NODE_ID=tinyaya-v6e16-eu) — same validated path as the restart; tmux
   `train` on all 4 hosts; `--resume auto` finds 65,250 in the r2 dir.
5. **Hard launch-verification gates** (abort + report if any fail):
   - log shows `Resuming training from step 65250` + optimizer + RNG
     restored (which dir it picked: `step_065250` vs `_final` — either is
     the same step; record it);
   - W&B re-attaches run id **xzcb60bl** (no new run);
   - first logged `train/lr_lora` ≈ 1.716e-4 and visibly DECREASING by the
     next log points (the scheduler is in the anneal — the whole point);
   - `step_066000` lands in the r2 GCS dir on schedule;
   - `train/audio_loss_full` still streaming; expected one-time
     `[ckpt] hub publishing DISABLED (storage limit)` line from the breaker
     (weights publish post-hoc via the suite script; samples/logs continue).
6. **Monitors**: step/LR/val poll (background) + qr_watch; ~8 h; final
   canonical save at 76,250.
7. **Post-run**: val trajectory report (did anneal beat 2.9048? new
   best_by_val); update PLAN/memory/capacity log + reval-report A.6
   footnote; extend eval targets per the runbook's anneal contingency
   (annealed best/final into Tier-1/2/3 + LAWA candidates); hub publishing
   of annealed checkpoints post-hoc (`publish_checkpoint_suite.py`,
   branches + `--main-folder`), within the storage budget (may need to
   swap 1–2 interim mid-run bundles for annealed ones — decide with data).
   Slice teardown decision then becomes fully live.
