## Headline

Six hyperparameter arms re-validated the v0.3 recipe as a **text+audio** speech-to-speech
translator on the full **1.24 M-pair** synthetic TR↔HI corpus — 5,000 steps (≈1.03 epoch)
per arm at global batch 256, one single-host TPU v6e-8 per arm. Winner: **arm D
(`lora_exclude_top: 0` — LoRA adapters on all 36 backbone layers)**. The previously frozen
champion recipe (arm A) finished **last at every composite weighting**: the re-validation
was not a formality.

Two context notes that make this run meaningful:
- v0.1–v0.2 trained **audio-only** on the false belief that the corpus shipped no text
  alignments; that was a two-bug misdiagnosis (wrong filenames in the check, wrong
  directory in the loader), corrected 2026-07-08 — the corpus has **100% alignment
  coverage** (840,426 src + 840,426 tgt word-level files). This sweep is the first
  supervised-text training in the project's history.
- Before this sweep's winner goes to production, the full shipping stack passed a
  **pipeline-validation gate** (32-sample memorization + checkpoint-reload + teacher-forced
  AND autoregressive inference examination) — see below.

**Selection notes:**
- The composite weighting question was resolved **analytically**: since the composite is
  a metric (not a training weight), the ranking was recomputed post-hoc from the logged
  `val/{text,audio}_loss` series at three weightings — it is **unanimous**
  (E ≺ D ≺ C ≺ F ≺ B ≺ A at 0.2/0.8, 0.4/0.6 and 0.5/0.5), so the choice of weighting
  does not affect the conclusion.
- **Gate adjudication** (pre-registered): cb0 accuracy must sit within ~0.5 pt of the best
  arm. E (−1.1 pt) and C (−1.2 pt) fail it; **D is the gates-clean winner** (−0.3 pt,
  second-best at everything else). Honest note: E's composite lead over D is 0.015
  (~0.4%); the **D+E combination** (exclude_top=0 *plus* the stronger regularization) was
  never tested and is the obvious future probe.
- All six arms pass the text gate by an order of magnitude (worst text CE 1.69 vs the
  11.5 stuck-at-random threshold).
- Arm F (unfreezing 2 frozen Moshi depth blocks) bought +0.06 pt mean CB1–7 over A at
  ~20% step-time cost — not carried into production.
- Key scientific read: **top-layer adapters are the text lever.** Removing the top-2
  layer exclusion (D) or adding regularization (E) both improve text CE by ~0.5 over the
  frozen champion at zero audio cost; rank (B: r64) and depth-unfreezing (F) do not.

## Appendix 3 (2026-07-12): the "global 256" was a ×8 fiction — real batch = batch × accum

**Finding.** Under SPMD, the logical (= global) batch is the DataLoader tensor's batch
dim; `mark_sharding` *distributes* those rows across chips, it never multiplies them.
The trainer's `effective_batch = batch_size × grad_accum × world_size` was a DDP
formula misapplied to SPMD. Every "global 256" in this report was really **32**
(b4 × accum8); the staged production config (accum 4) would have run at **16** — half
the validated batch; R3's "512" was 64. "3 epochs / 14,532 steps" was ~0.2 real epochs.
**All relative rankings in this report survive** — every compared run shared the same
semantics — but all absolute sample/epoch labels deflate ×8, which also explains the
capacity sweep's "overfitting isn't the constraint" (the model never saw a full pass).

**Evidence (P0 audit, code `6d7daf6`, v6e-8 slices `tinyaya-probe2-r1/r3`):**

| # | test | result |
|---|---|---|
| 1 | `scripts/tpu/spmd_batch_truth.py` on the live 8-chip mesh | batch-4 input keeps logical shape (4,16), spec `{devices=[8,1]0-7}`; 8-chip gradient **bit-identical (Δ≤1.2e-7)** to single-device on the same 4 rows |
| 2 | trainer smoke [`p0-shard-b4`](https://wandb.ai/cataluna84/tinyaya-stage2-tpu/runs/7cuwiqlo), in-loop print | `text_ids logical shape=(4, 300) spec={devices=[8,1]0-7}` — the arm recipe trains 4 rows/micro-step |
| 3 | A/B at identical real 32 samples/step: b4×8 vs [`p0-shard-b16`](https://wandb.ai/cataluna84/tinyaya-stage2-tpu/runs/p0-shard-b16) b16×2 | **14.58 → 2.78 s/step (5.2×)** at the same optimizer trajectory; HBM equal (~26 GB) |
| 4 | b32×1 (`p0-shard-b32`) | OOM by ~3% (18.98 G vs 18.46 G free) — falsifies "batch_size is per-chip" (32 rows/chip would overshoot ~8×) |

**Resume-correctness hardening (same audit) — verified live by a kill+resume drill**
(b4 smoke, GCS checkpoints, resume 60→100): optimizer state restored (**the GCS resume
path had NEVER restored optimizer state** — `os.path.exists("gs://…")` is always
False — every historical preemption resume silently reset Adam), host RNG restored,
`best_val`/patience restored, no post-resume LR spike, loss continuous within noise
(7.783→7.869→7.748…7.623). Fixes landed in `df8cde0`+`6d7daf6`: metadata.json uploads

is a hard error, scheduler LR primed before the first step (was: one full peak-LR
update on every start/resume), restored optimizer state materialized in its own XLA
graph (the drill's first attempt OOM'd when the transfer fused into step 61).

**Consequences for the production plan (supersedes the staging paragraph above):**
- The validated optimization is **real batch 32**. `train.per_chip_batch` (new) makes
  utilization explicit: **b16×accum2 keeps that optimization verbatim and runs 5.2×
  faster** (~2.78 s/step → 1 real epoch = 36,822 steps ≈ 28 h on one v6e-8).
- True-256 buys **no throughput** on v6e-8 (samples/s is pinned by rows/chip) and
  changes the optimization (R3 showed the text-CE risk); deferred to v0.4.
- Multi-host slices (v6e-16/32) add nothing until the `MpDeviceLoader minibatch=True`
  input pipeline exists — host-inconsistent inputs are UB; `per_chip_batch` refuses
  them. The prior v6e-16 production topology is withdrawn.
- Round-3 probes staged (launch on explicit approval): **R4** b16×accum2 equivalence
  vs round-2 R0 (same seed/schedule — curves must match at equal samples), **R5** WSD
  (plateau + 10% anneal) vs cosine for the early-stop-friendly long-horizon schedule.

### Topology audit addendum (2026-07-12): v5e-64 — where a big multi-host slice fails

A 64-chip v5litepod-64 spot slice (europe-west4-b; capacity granted in <10 min,
twice) was used to test the multi-host story at scale. It failed in three
instructive layers:

1. **Ops layer.** On v5e, `/mnt/data` is the 97 GB boot PD (not local SSD as on
   v6e): the 13 GB corpus untar wedged (1h33m elapsed, 2m43s CPU, kernel
   hung-task trace) and two hosts went fully SSH-dead — slice torn down. Fix
   that survives: a **39 MB smoke-data tarball** (4,000 train + 400 val rows,
   4,388 `.pt` + all 8,776 alignment JSONs) built with
   `scripts/build_sweep_subset.py`; startup drops to seconds. (Bonus finding:
   the manifest's `src/tgt_align_path` fields point at nonexistent names — the
   loader derives real `<pt-basename>.{src,tgt}.alignments.json` paths itself.)
2. **Rendezvous layer.** Per-host startup completes at different times, and
   torch_xla's SliceBuilder timeout is shorter than the spread: every trainer
   died with `Failed to establish SliceBuilder grpc channel to <peer>:8471`
   (3/16 hosts had not even finished startup). A multi-host slice needs a
   **simultaneous launch with a startup-completion barrier** — after a manual
   16-way simultaneous relaunch the mesh assembled cleanly.
3. **Model layer (the hard stop).** With 16/16 hosts up, the smoke produced the
   decisive multi-host print — `text_ids logical shape=(16, 300)
   spec={devices=[64,1]0..63}`, banner `global_batch=32` — i.e. **one host's 16
   rows spread over 64 chips; the other 15 hosts' loader work is discarded**
   (the Appendix-3 semantics, now demonstrated live at 16 hosts). Compile then
   OOM'd deterministically: `strategy=replicated` needs **27.58 G of 15.75 G**
   per-chip HBM (v5e = 16 GB vs v6e = 32 GB). The 5B composite cannot run
   param-replicated on v5e at all; it would additionally require fsdpv2-style
   param sharding (~160 MB/chip at 64-way) on top of the still-missing
   `MpDeviceLoader minibatch=True` input pipeline.

**Conclusion:** every multi-host topology (v6e-16/32, v5e-64) currently adds
zero training value — the input pipeline feeds one host's rows regardless of
slice size, and on v5e the model doesn't even fit. The v0.3 production vehicle
remains a **single-host v6e-8 at b16×accum2**. Multi-host is a v0.4 project
with three prerequisites: minibatch input sharding, (for v5e) param sharding,
and a rendezvous-aware launcher.

## Appendix 4 (2026-07-13): multi-host data parallelism for the v6e-16 production run

The long-horizon production run moves from single-host v6e-8 to **multi-host
v6e-16** (4 hosts × 4 chips). The blocker was that the trainer collapsed a
multi-host slice to ONE host's rows (SPMD replicated-input UB, proven on
v5e-64). This appendix records the pipeline that fixes it and makes v6e-16
deliver real data parallelism.

**Core mechanism (verified live).** `scripts/tpu/spmd_minibatch_truth.py` on a
real 4-host v6e-16 mesh: each host builds a distinct per-host batch of 8 rows
`(8,4)` from a `DistributedSampler`; `backend.shard_to_device(...,
minibatch=True)` assembles a **GLOBAL `(32,4)` logical tensor** sharded
`{devices=[16,1]0..15}` whose gather shows **all 4 hosts' distinct rows** —
real cross-host data parallelism, the exact opposite of the prior UB.

**Recipe (unchanged optimization, ~2× faster).** Real global batch stays **32**
(the validated optimum; R3 showed batch-64 loses): `per_chip_batch: 2` → 8
rows/host × 4 hosts = 2 rows/chip, `grad_accum: 1`. Same optimizer batch and
per-chip data as v6e-8's `b16×accum2`, but done in ONE micro-step across 16
chips instead of two across 8 → ≈1.7–2× faster/step. 3 real epochs =
`1,178,302/32 × 3 = 110,463` steps ≈ ~16 h/epoch.

**Implementation** (all gated on `multihost = is_tpu && host_count()>1`; the
validated single-host v6e-8 path is byte-for-byte unchanged): backend mesh
accessor + `set_global_mesh`, `process_index`/`local_chip_count`,
`shard_to_device`; per-host `DistributedSampler(num_replicas=host_count,
rank=process_index)`; train + val device transfer via `shard_to_device`;
`effective_batch × host_count`; `set_epoch(step)` on both rollover sites for
consistent shards; `bucket_frames` + multi-host refused.

**Operational spine for a multi-day spot run.** (a) GCS **rendezvous barrier**
in `startup_script.sh`: each host writes a ready-marker, all wait for the host
count (from the TPU worker-endpoint list) before launching — kills the
SliceBuilder gRPC race that is fatal on staggered per-host boots (fires on every
launch AND every preemption reboot). (b) **Opt-in GCS-backed XLA compile cache**
(`xla-cache-gs-uri`): restored at boot on all hosts, host 0 syncs back — survives
preemption so the ~20-min recompile is paid once, not every resume. (c)
**Async checkpoint upload** so keep-all saves don't stall the loop. (d)
**Flash-attention toggle**. Each opt-in + Phase-E-gated.

**Public checkpoint suite.** Log-spaced saves {1,2,4,…,512} (Pythia convention)
∪ every 1000, keep-all + async upload; `scripts/publish_checkpoint_suite.py`
mirrors the trajectory to one HF repo, one `step-N` branch per checkpoint
(weights-only; optimizer/scheduler/rng stay in GCS); LAWA averaging at the end.

**Status.** Pipeline built, committed, unit-tested (134 tests, seam clean);
core primitive validated live on 4 hosts. End-to-end trainer validation on a
healthy co-located EU v6e-16 (equivalence vs R4/R0, 4-host kill/resume drill,
WSD anneal) is pending spot capacity. Production config staged
(`configs/tpu/stage2_tpu_v6e16_full_v03_mh.yaml`); launch gated on the Phase-E
verdict + team sign-off + explicit user word.

## Addendum (2026-07-14): pre-launch hardening pass

Before the long-horizon run, a dedicated hardening review (user-requested) of
(1) the 4-host parallelization design, (2) the checkpoint-to-bucket strategy, and
(3) remaining long-horizon failure modes — informed by an Exa deep-research pass
on HF-CDN failures + multi-day spot-TPU practice. Code: commits `8fcb082` (fixes)
+ `5a21d24` (probe configs/runner). **Two live, silent failure modes were found
and closed** (§A.3).

### A.1 Parallelization: what runs, and why the alternatives lose

The long run uses PJRT **SPMD, one process per host**, a 1-D 16-chip mesh (axis
`"fsdp"`, used purely data-parallel), **replicated weights** (`auto → replicated`:
192M trainables < the 500M FSDP threshold; the frozen ~5B of the 5.24B bf16 model fits
32 GB HBM/chip at 2 rows/chip with scan + grad-checkpoint), and the minibatch
input pipeline: per-host `DistributedSampler(num_replicas=4, rank=process_index)`
draws 4 disjoint corpus shards; `shard_to_device(minibatch=True)` assembles
per-host (8,300) into the global (32,300) batch. Verified bit-exact by the
gradient-identity probe; ~1.85 s/step steady (≈1.9× the v6e-8 b16×accum2
equivalent, same optimizer batch 32, `accum 1`). Epoch rollover uses
`set_epoch(step)` — all hosts reach the same step, so shards stay consistent.

Alternatives rejected on evidence: (a) *naive replicated-input* — silent data
loss, only host-0's rows survive `mark_sharding` (proven live on v5e-64); (b)
*FSDPv2 weight sharding* — pointless at 192M trainables, adds DCN all-gathers,
and carries the PEFT save-on-device deadlock; (c) *xmp.spawn DDP-style* — legacy,
incompatible with the SPMD mesh + scan; (d) *global batch 64* — R3 showed
batch-64 loses quality (multi-host buys wall-clock, never sample efficiency);
(e) *multislice / v6e-32/64* — spot un-gettable (10/10 prober FAILs) + megascale
complexity for zero sample-efficiency gain.

### A.2 Checkpoints: everything routes to the bucket (audit PASS) + manifest

Audit of the long-run config against the code: `save_dir` is the EU bucket;
`keep_last_n: 0` ⇒ `prune_checkpoints` no-ops (unlimited retention); log-spaced
{1,2,4,…,512} **plus** `save_every: 1000`; every save stages locally and uploads
with the **metadata-last atomic gate** (4-retry gsutil); periodic saves upload on
the background single-worker executor (`async_checkpoint_upload`), drained before
the final save; `best_by_val` + final canonical stay synchronous. Expected
volume ≈ 122 dirs × 4.23 GiB (measured live, probe 1a) ≈ **516 GiB ≈ $12/mo**
(EU standard). New in
`8fcb082`: `metadata.json` now carries a `files: {name: size}` **integrity
manifest** (metadata itself stays the completeness gate), so audits can verify a
step dir exactly. Accepted behaviors (documented, unchanged): a preemption
mid-async-upload loses that one un-gated periodic snapshot; `best_by_val` uploads
synchronously (~30–60 s per improvement); data order across a resume is
at-least-once (RNG + sampler epoch restored, no dataloader cursor).

### A.3 Two silent failure modes, found live and closed (`8fcb082`)

1. **Staging identity.** `startup_script.sh` skipped staging whenever
   `/mnt/data/encoded/.unpacked` existed — a contentless marker. All 4 hosts held
   the 4k spoke-4 subset behind that marker, so launching the long run with the
   full-corpus tarball would have **silently trained 110k steps on 4,000 rows**.
   The marker now records its source (tarball URI / `hf:<dataset>`); any mismatch
   wipes `encoded/` + `splits/` + alignment JSONs and re-stages.
2. **Text-coverage.** `dataset.py` zero-fills the text stream when alignment
   JSONs are missing; the in-code guard (`require_alignments`) is fatal only at
   **zero** sampled coverage — partial loss stays silent (the arm-era
   under-trained-text mechanism). New boot **preflight** counts split rows / .pt
   / alignment pairs + `train.jsonl` md5, gates on `expected-train-rows` and
   `min-text-coverage` metadata, and rides the digest on the rendezvous
   ready-marker: hosts **refuse to launch on divergent corpora**
   (`DistributedSampler` shards by index — divergent splits silently corrupt the
   global batch).
