# Plan: v0.3 long-horizon re-validation sweep → production run → eval (TPU multi-slice)

> Status: approved 2026-07-07. Supersedes the "recipe frozen, run held" state in
> [`v0.3-public-release-plan.md`](v0.3-public-release-plan.md) — the production run now
> waits on the Phase-1 re-validation winner. Tick phases as they land.

## Context — why this exists

The frozen v0.3 recipe (`r=32, lr_lora=1.716e-4`, +MLP, rsLoRA) was picked by a sweep that
ran **1,500 steps (10% of the production horizon) on the 200K subset (0.3 epoch-equivalent)**,
ranked by `val/composite` alone — and the per-codebook accuracy metric was **broken during
every sweep** (fixed `8854698`), so there was never any signal on the CB1–7 depth path.
Several axes were never swept at all: `exclude_top`, data-rich-regime dropout/wd (set by
fiat), the depth-path LRs (`lr_projection`/`lr_audio_embed`=5e-4, `lr_depth`=1e-4, carried
since v0.1), `per_codebook_multipliers`, label smoothing. The user is (rightly) skeptical;
before committing the 14,532-step production run, re-validate at a longer horizon on the
full corpus with the **now-trustworthy pipeline** (per-CB acc `8854698` + checkpoint
scan-remap loader `eb17609`).

**Hard constraints:**
- TRC grant expires **~2026-08-03** (~4 weeks). TPUs are free; never provision outside the
  granted zones; everything below stays in `europe-west4-a` (bucket co-location — no
  cross-region egress; us-east1-d only as overflow WITH a scratch US bucket).
- Quota: **64 v6e chips spot in ew4a** → 5× v6e-8 (40 chips) in Phase 1; later 1× v6e-16
  (16) + 1× v6e-8 (24) concurrently. Nothing is provisioned right now.
- v6e-8 is **single-host** → parallel arms need NO multi-host coordinator; plain launches.
- Global batch pinned at **256** everywhere: v6e-8 = `batch_size 4 × grad_accum 8 × 8 chips`
  (v6e-16 uses `grad_accum 4`). Recorded ~6 s/step ⇒ 5k-step arm ≈ **8–9 h**.

**User decisions (locked):** production starts **fresh from step 0** on the v6e-16 (clean
single public W&B run; no cross-topology resume) · depth-path mini-sweep runs **only if**
Phase 1 shows CB1–7 lagging · user then asked to widen the axis audit → Phase 1 grows to
**6 arms** (adds the `depth_unfreeze_blocks` probe, still within quota: 48/64 chips).

## Phase 0 — capacity report + trust-the-logs gate (~½ day, 1× v6e-8)

**0-pre. Persist this plan in the repo**: commit it as `docs/v0.3-reval-sweep-plan.md`
(user ask), cross-linked from `docs/v0.3-public-release-plan.md`.

**0a. Capacity report (local, no TPU).** New `scripts/report_capacity.py`:
- Instantiate the composite model (CPU) at the candidate configs; print trainable params
  **by component** (backbone LoRA, embed_tokens LoRA, audio_heads, projection,
  model_audio_embed, text_embed). Ground truth so far: 122M trainable at the r=16-era
  config (live audit 2026-06-24); r=32 +MLP will differ — get exact numbers.
- Dataset stats from the splits jsonl metadata: n samples, frames histogram, CB0-supervised
  tokens/epoch (≈ samples × avg_frames), all-CB target tokens/epoch (×8). Emit
  **tokens-per-trainable-param over 3 epochs** per arm — the "is r=64 oversized / is r=16
  starved" number, documented for release-plan §5.
- Reuse the model-construction path from `scripts/train_hierarchical.py` (no new model
  code); follow `tpu-doc-style`.

**0b. Metric/e2e gate on HEAD (v6e-8 — the "tests on logs" ask).** 32-sample overfit run
(existing overfit config/gate), PASS =
- all 8 codebooks ≥ ~90% **delayed-target** accuracy in the training val
  (`val/per_codebook_acc_{i}` visible in W&B), AND
- a saved checkpoint reloaded by `scripts/eval_checkpoint.py` (scan-remap loader `eb17609`,
  which raises on any unfilled LoRA tensor) reproduces TF per-CB within ~1 pt of the
  training val. This certifies the exact metric+checkpoint+eval loop the sweep relies on.

**0c. Full-corpus GCS staging (one-time).** Only the 200K subset exists in
`gs://tinyaya-stage2-eu/data/`. Build `full-corpus-<date>.tar.gz` (~10 GiB est., scaling
from 200K→1.6 GiB): download the HF corpus **on the v6e-8** (fat pipe), tar, upload. Reuse
the existing `SWEEP_DATA_GS_URI` staging mechanism in `scripts/tpu/startup_script.sh` (same
`.unpacked` marker) — verify it accepts a full-corpus URI; heed the v03 config header's
warning: clear `/mnt/data/{encoded,splits}` + stale boot metadata or the host silently
keeps the 200K subset.

## Phase 1 — 6-arm × 5,000-step full-corpus re-validation (~1 day wall-clock, 6× v6e-8 parallel)

**Not a W&B bayes sweep** — a deterministic parallel grid, one arm per v6e-8, plain
single-host launches (`launch_spot.sh TRC_PROFILE=v6e-8-eu` with per-arm `QR_NAME`/`NODE_ID`
+ CLI overrides), W&B group `v03-5k-reval`, deterministic run names + `--resume auto`
(sweep-hardening lessons: checkpoint-truth completion, no false-complete). All arms: +MLP
structure, rsLoRA, α=2r, batch 256 (`grad_accum 8`), 5,000 steps ≈ 1.03 epochs.
Base config: derive `configs/tpu/stage2_tpu_v6e8_reval.yaml` from the v03 production config
(grad_accum 8, max_steps 5000, save_dir `…/stage2-reval-5k/<arm>`). Arms A–E use existing
CLI flags (`--lora_r --lr_lora --lora_dropout --weight_decay --lora_exclude_top`); arm F
needs a **tiny prep patch** exposing `--depth_unfreeze_blocks` (+ `--lr_depth_blocks`) in
the `--sweep` args block (`train_hierarchical.py` ~:942–959, mirrors existing flags; the
plumbing already exists — `lora.depth_unfreeze_blocks` → `unfreeze_last_n_blocks` at :1093,
`lr_depth_blocks` param group at :515).

| Arm | r | lr_lora | overrides | purpose |
|---|---|---|---|---|
| A | 32 | 1.716e-4 | — | frozen winner (champion) |
| B | 64 | 1.2e-4 | — | capacity-up (horizon may favor it) |
| C | 16 | 2.4e-4 | — | capacity-down control |
| D | 32 | 1.716e-4 | `exclude_top=0` | backbone depth-coverage probe (never swept; watch HBM <30/32 GiB) |
| E | 32 | 1.716e-4 | `dropout 0.10, wd 0.05` | long-horizon regularization probe |
| F | 32 | 1.716e-4 | `depth_unfreeze_blocks=2` (`lr_depth_blocks=1e-5`) | **CB1–7 capacity probe** — the only lever that trains the frozen Moshi depth blocks; directly measurable now via fixed per-CB acc; watch HBM (extra optimizer state) |

**Selection rule (uses the fixed pipeline — the user's explicit ask):**
1. Primary: `val/composite` at step 5,000 (and min-over-run).
2. **Per-CB accuracy gates** (fixed metric): mean CB1–7 delayed-target acc climbing and
   within ~1 pt of the best arm; CB0 within ~0.5 pt. A loss-winner failing an accuracy
   gate is disqualified.
3. Horizon tiebreak: slope of `val/composite` over steps 3,500→5,000 (still descending vs
   flat) — predicts the 14.5k ranking better than the level.
4. Health: no NaN, sane grad-norm, HBM headroom (arm D especially).

Measure real s/step at ~step 100 and update the ETA. Tear down all 6 QRs when arms finish.
Arm F extra read: if it beats A on CB1–7 acc *without* hurting `val/composite`, carry
`depth_unfreeze_blocks=2` into the production config (and note the checkpoint grows by the
unfrozen depth blocks).

## Phase 2 (CONDITIONAL) — depth-path/loss-shaping mini-sweep

Trigger: Phase-1 mean CB1–7 acc badly trails CB0 (guide: CB1–7 <60% while CB0 >75%) AND
arm F didn't already fix it. If triggered: extend the same CLI patch to expose
`--label_smoothing --per_codebook_multipliers --lr_projection --lr_audio_embed
--progressive_unmask_fraction --num_full_ft_layers`; then 4–6 arms × 2,500 steps on
v6e-8s, prioritized from the audit table: multipliers {flat, current, steeper} ×
lr_depth {1e-4, 3e-4} × label_smoothing {0, 0.1}; deeper cuts if warranted:
`progressive_unmask_fraction` {0, 0.10, 0.25}, `num_full_ft_layers=2` (HBM permitting),
`min_lr_ratio` {0, 0.1}. Same selection rule. Can run on freed v6e-8s in parallel with
Phase 3.

## Phase 4 — checkpoint averaging + eval (the never-executed v0.3 Phase-A ⭐)

- New `scripts/average_checkpoints.py`: offline LAWA/SWA-style average of the last K∈{3,5}
  checkpoints (and a window around `best_by_val`) — average LoRA A/B + trainable heads,
  re-save in the standard checkpoint layout so `eval_checkpoint.py` loads it unchanged.
  Pure post-processing (all ckpts kept every 500 steps).
- Eval per release-plan §3, comparing **best_by_val vs final vs averaged**:
  - TF per-CB accuracy on the FULL held-out val via the training-val path on a v6e-8
    (fast, fixed metric).
  - `eval_checkpoint.py`: AR generation + ASR-BLEU (faster-whisper large-v3 **int8 on
    CPU**, 30–50 samples, `undo_codebook_delay` decode per `520b636`) + DNSMOS/UTMOS.
  - State the protocol (ckpt, ASR backend+version, decoding, seed, #samples) for the card.
- Champion → v0.3 card; then the release checklist (publish ckpts/cards/blog, **rotate
  leaked HF/W&B tokens before going public**).
