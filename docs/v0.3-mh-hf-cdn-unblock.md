# v0.3 multi-host (v6e-16) — HF backbone download blocker & WARP-proxy unblock

**Date:** 2026-07-14 · **Branch:** `feat/v0.3-implementation` · **Slice:**
`tinyaya-v6e16-eu` (v6e-16, 4×4, europe-west4-a) · **Phase:** E (full-probe
re-validation), spoke 4 (WSD anneal).

## TL;DR

The multi-host trainer could not resume because the two HF backbones it loads at
model-build time would **not download** onto the GCP-EU TPU hosts — every transport
stalled at tens–hundreds of MB at ~0 MB/s. Root cause is a **network route**
problem, not auth/rate-limit/transport: HF geo-routes this GCP-origin EU host to a
**US** CDN gateway (`us.gcp.cdn.hf.co`) over a congested transatlantic path, and the
Xet path is separately known to stall on GCP. Fix that measured **29.4 MB/s** (vs
249 B/s): route the download through **Cloudflare WARP in proxy mode** (SOCKS5,
egress via the Amsterdam edge) using the **plain, proxy-honoring** HF downloader
(`HF_HUB_DISABLE_XET=1` + `HF_HUB_ENABLE_HF_TRANSFER=0`). Training's GCS/DCN are
untouched (proxy mode doesn't change the default route).

## Where it blocked

Spoke 4 (WSD anneal, `configs/tpu/reval/mh_wsd_fast_v6e16.yaml`) is checkpointed at
`step_001500` in `gs://tinyaya-stage2-eu/checkpoints/mh-wsd-fast/v6e16/`; only the
150-step anneal (1500→1650) remains. On launch the trainer rebuilds the composite
model, which loads two HF backbones from the host cache:

| repo | files | size | notes |
|------|-------|------|-------|
| `CohereLabs/tiny-aya-base` | 2 shards | 6.7 GB | shard-1 present; shard-2 was partial (256 MB `.incomplete`) |
| `kmhf/hf-moshiko` | **4-shard bf16 set** (`-of-00004`) | **~15.6 GB** | `surgery.extract_depth_decoder_state_dict`, `composite.py:234`; repo hardcoded, not config/env-overridable. Repo also ships a 31 GB `-of-00007` fp32 set we skip via `ignore_patterns=["*-of-00007.safetensors"]` |

On the current fresh-boot hosts both were missing/partial. The trainer hung at
`Loading Moshiko for depth decoder extraction… Downloading shards: 0/4`.

## Diagnostic trail (evidence)

1. **Host-direct pull stalls across all transports.** Xet, `hf_transfer`, and plain
   HTTP each froze at 3–514 MB with **0 MB/s** growth. Three different code paths
   converging on the same failure ⇒ the shared **network hop**, not a transport bug.
2. **Not auth / not rate-limit.** Token valid (37 ch, `hf_` prefix); authenticated
   `GET /api/whoami-v2` → **HTTP 200**, no `RateLimit`/`Retry-After` headers. (A true
   quota returns 429 + headers, not a silent 0 MB/s stall after partial bytes.)
3. **Geo-misrouting to a US gateway.** `fast.hf.co` from the host = **3.8 KB/s**
   (resolved to an AWS us-east IP). The download redirect for a Moshiko shard sends
   this EU host to **`us.gcp.cdn.hf.co`** (a *US* GCP gateway, 34.117.89.69) — a
   transatlantic hop.
4. **No EU GCP gateway exists.** `eu.gcp.cdn.hf.co` / `europe.gcp.cdn.hf.co` /
   `gcp.cdn.hf.co` all **NXDOMAIN**. Only `us.gcp.cdn.hf.co` resolves.
5. **CDN edge is server-side, by repo storage region.** Confirmed via HF forum
   (an EU-region repo is served from `cdn-lfs-eu-1` even to US clients). `kmhf/hf-moshiko`
   is US-region, so it's pinned to US edges. `HF_ENDPOINT` only changes the API host,
   **not** the CDN redirect — there is no client env override for the edge.
6. **Matches known HF issues.** [xet-core#800](https://github.com/huggingface/xet-core/issues/800)
   — "Xet-backed downloads stall on GCP (works when `HF_HUB_DISABLE_XET=1`)", same
   ~123 MB stall signature; [#821](https://github.com/huggingface/xet-core/issues/821)
   — CloudFront edges capped ~8.7 MB/s.

Host-side fixes were exhausted and did not help: valid token, `max_workers=1`,
`HF_HUB_ENABLE_HF_TRANSFER=1` (Rust multipart / classic cdn-lfs) — still stalled at
3–131 MB. The route, not the client, is the bottleneck.

## The fix (measured on w0)

**Cloudflare WARP, proxy mode** (`warp-cli mode proxy`, SOCKS5 on
`127.0.0.1:40000`). Proxy mode does **not** alter the host default route, so SSH,
GCS, inter-host DCN, and the metadata server all stay on the internal EU route; only
clients that explicitly point at the SOCKS proxy egress via Cloudflare. WARP egresses
this host via Cloudflare's **AMS (Amsterdam)** edge, so the request is no longer
GCP-origin and HF stops routing it to the US gateway.

Read-only throughput probe (50 MB range GET → `/dev/null`), worker 0:

| path | throughput | CDN chosen |
|------|-----------|------------|
| direct (GCP-EU origin) | **249 B/s** (stalls) | `us.gcp.cdn.hf.co` (US) |
| **via WARP proxy (AMS)** | **29.4 MB/s** ✅ | `cas-bridge.xethub.hf.co` |

~120,000× improvement ⇒ ~9 min/host for the 15.6 GB Moshiko set.

**Transport constraint:** `hf_transfer` and the Xet client do **not** honor SOCKS
proxies (per HF docs + issues #1780/#3603), so the download must use the **plain**
downloader so it actually rides the proxy and stays resumable:

```
HF_HUB_DISABLE_XET=1
HF_HUB_ENABLE_HF_TRANSFER=0
ALL_PROXY=socks5h://127.0.0.1:40000
HTTPS_PROXY=socks5h://127.0.0.1:40000
HF_HUB_DOWNLOAD_TIMEOUT=20      # clean-exception resume on stall
# snapshot_download(..., max_workers=1, ignore_patterns=["*-of-00007.safetensors"])
# requires PySocks in the env: `uv run --with 'requests[socks]'` if absent
```

5. Relaunch the anneal on `--worker=all` (mirror `scripts/tpu/_remote_redeploy.sh`
   INNER: `uv run … scripts/train_hierarchical.py --config
   configs/tpu/reval/mh_wsd_fast_v6e16.yaml --resume auto`; XLA env incl.
   `XLA_NO_SPECIAL_SCALARS=1`; secrets from Secret Manager on-host). Backbones
   cache-hit → resume `global_step=1500` → WSD anneal → **step 1650**.

### Fallback — local-box relay
The local box is on a different, well-routed ISP (it pulled tiny-aya shard-2 in
seconds). Sequential single-file `hf_hub_download` locally → `gcloud storage cp` to a
transient `gs://tinyaya-stage2-eu/tmp/…` → intra-EU pull + inject into each host's HF
cache (`blobs/<etag>` + `snapshots/<rev>/<file>` symlink) → delete transient →
relaunch. Already proven this session for tiny-aya shard-2.

### Recommended durable follow-up (de-risks Phase F production)
Stage both backbones to `gs://tinyaya-stage2-eu/model-cache/` and have
`scripts/tpu/startup_script.sh` inject them intra-EU on boot. The repos are
US-region, so this route problem **recurs on every fresh boot / preemption** — a
one-time EU-resident copy removes the CDN dependency for the multi-day production run
entirely.

## RESOLUTION (2026-07-15): fixed upstream — HF-direct is primary again

Retested from the same EU hosts, no proxy, default transports (Xet on):
the resolve redirect now points to **`cas-bridge.xethub.hf.co`** (the US
gateway `us.gcp.cdn.hf.co` is out of the path entirely); mimi 385 MB in
2.6 s (**146 MB/s**), a 4.97 GB moshiko shard in 22.7 s (**219 MB/s**) —
vs 249 B/s the day before. Consistent with HF's announced GCP CDN-gateway
rollout / an xet-core#800-class fix.

`prefetch_backbones.sh` is now **direct-first** (default transports, hard
`timeout 900` so a route regression fails fast) with the WARP+plain-downloader
flow retained verbatim as the fallback. `HF_HUB_OFFLINE=1` gating stays
regardless (revision pinning + immunity to future regressions mid-run). A
full fresh-provision drill (wipe all model+dataset caches, re-download
everything HF-direct on all 4 hosts) validates the path end-to-end — results
in the reval report addendum.
